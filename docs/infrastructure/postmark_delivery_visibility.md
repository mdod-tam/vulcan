# Postmark delivery visibility operations

## Dependency and deployment order

This feature builds on PR 217 at `d66a14b70d49ea390c268c1fd08447216efad9f6` plus the reviewed 32-path correction snapshot `c779a8b63728`. The snapshot includes routing, secure-request outcome, locale and print-identity repairs. Deploy those corrections with this feature; the new visibility code assumes their channel and local-outcome contracts. The implementation worktree records the verified dependency inventory separately from the feature delta. No provider configuration or live send is part of implementation verification.

1. Apply prerequisite migrations through `20260928150000`, then `20260929180000_create_email_delivery_attempts`. The additive migration creates attempts and minimal event receipts; it does not backfill provider IDs or infer historical success. Configure stable Active Record encryption credentials and the application's stable secret key before accepting traffic. Destination addresses are encrypted; recipient lookup keys use a keyed digest derived from the application key generator.
2. Supply `POSTMARK_SERVER_ID` to every web and worker process, and `POSTMARK_WEBHOOK_USERNAME` and `POSTMARK_WEBHOOK_PASSWORD` to web processes. A missing or blank server ID prevents Postmark handoff; no placeholder server identity is recorded. Test and letter-opener transports do not create Postmark attempts. Use dedicated, strong webhook credentials with no defaults. The send adapter reads `credentials.postmark_api_token`; polling uses that same credential, with `POSTMARK_API_TOKEN` as its environment fallback. They must name the server identified by `POSTMARK_SERVER_ID`.
3. Deploy application and worker code together, then restart workers and the recurring-job scheduler. Verify the `poll_email_delivery` recurring job is scheduled hourly. The database is shared across worktrees in local development: migrate only test during verification, and serialize test runs.
4. After deployment, configure feedback separately for both used streams, `notifications` and `outbound`, in the intended Postmark server. Point the HTTPS webhook at `/webhooks/email_events`; use Postmark's HTTP Basic authentication settings with the exact configured username/password. Enable Delivery, Bounce and SpamComplaint. Open is optional for messages already tracked; use first-open-only and do not enable new tracking just for this UI. Keep bounce/complaint `IncludeContent` disabled. Leave the separate inbound-email hook unchanged.
5. Verify authentication first using synthetic payloads in an authorized environment: missing/wrong credentials or missing configuration returns 401; an incorrect `ServerID` or malformed supported event returns 422. Valid unmatched events return 200 without creating a user, request or attempt. Only after separate authorization, use a controlled real message to confirm each stream's provider ID, delivery feedback and masked display. Do not paste credentials, email bodies or secure URLs into logs or tickets.

Postmark supports [HTTP Basic authentication for webhooks](https://postmarkapp.com/developer/webhooks/webhooks-overview); it does not provide the custom HMAC scheme used by sibling controllers. The email controller skips only that inherited check and installs its own required authentication. Credentials and `ServerID` must both match. No test-only controller or fallback secret authorizes email events.

## Attempt and feedback contract

`EmailDeliveryAttempt` is the transport owner. It is not an outbox and does not create user-facing notifications. Each logical envelope has an opaque correlation ID and one attempt row per distinct destination. An advisory transaction lock serializes the correlation even if a retry rebuilds a different address. Unique database indexes enforce correlation/destination and server/provider-message/destination identity. One provider message can therefore produce independent feedback for several recipients. A new issuance/resend gets a new correlation; replay of an accepted or uncertain job does not transmit again or relabel an accepted attempt as locally suppressed.

Before handoff, capture links the actual request (when present), application, logical recipient and selected destination owner. It encrypts the address used at that moment. An external medical provider need not be a `User`; its destination is preserved without looking up a user by email. Later contact edits do not rewrite history. The only new external metadata is the opaque `delivery_attempt` correlation. Bodies, secure links, credentials, raw headers and provider diagnostics are not stored in attempts/receipts or displayed in the component.

The common mailer boundary covers immediate sends, mail delivery jobs, certification wrapper jobs and fallback mailers. `X-PM-Message-Id` is the provider identity; RFC `Message-ID` is stored separately and is not used to poll Postmark. If the provider accepts but the acceptance write or subsequent notification bookkeeping fails, the link remains active and no automatic resend occurs. The pre-send row remains available for an early/later correlated callback. Operational instrumentation `tracking_failed.email_delivery` contains only the error class. Investigate an unknown attempt before explicitly issuing a new send. HTTP 429/503 refusals and DNS/connection-refused failures can retry, with at most three job executions. The whole envelope must still have only confirmed failed rows, with no provider/feedback facts and the same destinations and server. The existing advisory lock claims those rows as unknown before transport, so concurrent retries cannot send twice. HTTP 401/404/413/415/422 refusals remain failed and require configuration/input repair; they are not automatically retried. A timeout, connection reset or HTTP 500 remains unknown and cannot replay automatically: Postmark may have accepted it. See the [Postmark response contract](https://postmarkapp.com/developer/api/overview). Staff should investigate these outcomes and, when appropriate, deliberately issue a new request from the application. No production-data repair is needed before the first deployment.

The installed `postmark` 1.25.1 SDK converts top-level JSON keys to underscored symbols; nested `MessageEvents` keep string keys. Separate webhook and SDK normalizers feed one locked updater. Top-level `Queued`, `Sent` or `Processed` do not prove delivery. See the [Messages API](https://postmarkapp.com/developer/api/messages-api) and [Delivery payload](https://postmarkapp.com/developer/webhooks/delivery-webhook).

Feedback matches server, provider ID and destination digest; before acceptance is saved it may match opaque correlation and the same destination. A conflicting provider ID is rejected. Each receipt key hashes event kind plus provider event ID (bounce/complaint ID), or kind plus the event's microsecond timestamp when no ID exists. The attempt supplies recipient/message scope. Duplicate and out-of-order deliveries preserve independent earliest delivery, bounce, complaint, open and delay timestamps; adverse facts remain visible after a later open or delivery. Raw bounce explanations are reduced to an allowlisted category. See [Bounce payload](https://postmarkapp.com/developer/webhooks/bounce-webhook) and [Spam complaint payload](https://postmarkapp.com/developer/webhooks/spam-complaint-webhook).

A confirmed bounce records one `email_bounced` Event per attempt, linked by `bounce_event_id`, in the same transaction as feedback and receipt. `PublicAuditActor.system_audit_actor_or_report` is lookup-only. If the configured system audit actor is absent, feedback still commits and the missing actor is reported; a repeated callback can repair the breadcrumb after the actor is restored. Never create/promote a substitute user to repair tracking. Other audit-write failures roll back the update so Postmark can retry. No ordinary sent/delivered/open audit events are added. Feedback never resends, reactivates contacts, revokes links or transitions application workflows.

## Bounded refresh and history

The hourly `EmailDelivery::PollJob` checks up to 100 oldest eligible attempts. Admin-only manual notification refresh and `notification_tracking:check_all` share the same budget: eight checks total, at least one hour apart, within seven days of the attempt. A lock claims each check before network I/O. Confirmed delivery, bounce, complaint or definite transport failure stops polling. Opens are optional secondary facts and never extend the budget. Attempts from a different configured server are not queried with the current server token.

Refresh failure records `check_failed_at`; exhausted/expired tracking shows the lack of a recent update alongside existing facts. It never converts a confirmed result into a sending failure. Accepted but unconfirmed attempts become delayed after 24 hours. Details distinguish never-tracked legacy requests from an uncertain tracked send, and show request time separately from established acceptance time. In the notification list, recipients see only basic delivery status for their own notifications; suppression reasons, destination ownership, provider feedback, open history and other tracking details remain admin-only.

Legacy notification IDs and status enums are not migrated into attempts. Mixed-version workers can still produce untracked sends, so complete the worker restart before relying on coverage. Contexts captured by the prerequisite but lacking a correlation use a stable hash of their request ID; older unsupported contexts retain the prerequisite's fail-closed behavior. Untracked notifications have no delivery panel; recorded local outcomes and actual unknown attempts remain visible. The backfill/analyze tasks only report; duplicate cleanup cannot infer duplicate sends from request counts. The obsolete `EmailEventHandler`, `WebhookRetryJob` (no enqueue callers) and numeric provider-status ranking are removed; outbound webhook retries now belong to Postmark.

Print display reuses the print lifecycle and a batch-loaded display snapshot of current controls/identity. That snapshot is only for rendering: actual release still rechecks policy under locks. SMS shows submission only from its own evidence. DocuSeal invitations retain their existing provider/request/signing evidence; additional SMS or DocuSeal delivery integration remains follow-up work.

## Rollback

Disable the new outbound webhooks and hourly feedback schedule before rolling application/workers back. Keep the additive tables and data for investigation; do not run a destructive down migration while any new process is running. Previous code ignores the new tables, and provider feedback never overwrites legacy notification status. A rollback loses visibility for new sends and may restore old tracking behavior, so avoid legacy backfill/check jobs. Do not re-enable the old email webhook contract. Preserve the prerequisite corrections and inbound webhook configuration. Resolve unknown attempts manually before resending; rollback is not evidence that an email failed.
